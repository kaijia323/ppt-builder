- 场景：{{scenario}}；听众：{{audience}}；汇报目的：{{purpose}}

{{adaptive_rules}}
请依次完成：

1. profile（文档画像）
   - doc_kind：文档是什么（如“投标技术方案”“需求规格说明书”“开题报告”）
   - judged_by：听众拿什么来衡量这份文档，2—5 条（如“是否完整响应招标要求”“技术路线是否可行”“指标能否达到”“能否按期交付”）
   - core：一句话说清这份文档主要在讲什么

2. units（内容骨架）：这份文档在讲的几项“{{skeleton_by}}”，2—8 个，按原文顺序。
   - name：单元名称，用原文的叫法，4—14 字
   - sections：讲这个单元“怎么做/做什么”的主要章节键（写到能完整覆盖的层级，如 D1-S5.2）
   - overview_sections：原文另有概要处简述同一单元时，填那个概要章节（如“项目建设内容”下的对应小节），没有填 []
   - metric_sections：与该单元直接相关的指标、成果要求章节（如“成果主要技术指标”中对应的小节），没有填 []
   - summary：一句话说明这个单元包含哪些部分
   units_title：这些单元合起来在原文中的叫法（如“服务内容”“建设内容”“建设任务”），用作汇报中的章名
   注意：骨架是“文档在讲的建设内容”，不是章节顺序本身。上面【原文平行结构】的每一行是同一项内容，归同一个单元（主体放 sections，概要放 overview_sections，指标放 metric_sections）。
   单元粒度跟原文自己划分的建设任务一致：一节业务需求对应几节功能实现时，这几节是一个单元的组成部分，不要各拆成一个单元。同一单元在原文中分散在“概要”“技术方案”“指标”几处时，都归到这个单元里，不要各算一个单元。

3. shell（外壳对应）：外壳中的每个模块，在原文中对应哪些章节（sections）。
   - 外壳模块是“听众必问的问题”，不是原文必须有的章节：原文没有对应内容的模块填 []（标“必设”的模块除外，必设模块要从原文各处找到依据）
   - label：这一章在汇报中的名称，用原文的叫法（如原文叫“项目建设的必要性”就写这个），没有合适叫法时省略
   - 原文有、但不属于任何骨架单元和外壳模块、又对听众判断重要的内容（如续建项目的“上期建设成效”、篇幅很大的“数据安全方案”），
     可以新增一个外壳模块：module 用原文叫法，after 写放在哪个模块之后（填模块名；放在骨架单元之后填“骨架”）。信息量低的内容不要新增，放进 low_info
   - 已经归入骨架单元的章节不要再放进外壳（如“模型部署”属于智能体单元，就不要放进“总体技术路线”）；外壳只放不属于任何单元的章节。
   - 标为“原文有依据才设”的模块（如保障与亮点）：原文没有专章时，把分散在各处、能作为依据的小节也列出来
     （如“质量控制”“测试与试运行”“安全约束”“兼容适配”所在小节；可以是骨架单元内的小节，这是唯一允许与骨架重叠的情况），
     note 中说明是“分散依据”；确实没有任何依据才填 []。

4. special（特殊章节）：
   - overview_impl：原文中“概要 + 实现”两处讲同一套内容的章节对（如“项目建设内容”与“项目技术方案”），汇报时概要只作一页总览、实现展开成章
   - metric_chapters：集中写指标、成果要求的章节（汇报时分散到对应单元的页面，结尾汇总）
   - low_info：信息量低、不单独成页的章节（参考标准清单、附件明细、逐项资料清单、填表说明等），写 reason
   - parallel：内容平行、会复述同一组要素的章节组（如“业务需求”与“功能需求”、“研究目标”与“拟解决的关键问题”），写 reason

5. questions（汇报要讲清的问题）：5—8 个，是这批听众看了这份文档后最想听汇报人讲清楚、原文也有内容可以回答的具体问题。
   - 要具体到这份文档（✗“技术是否可行”；✓“三个院区的号源如何统一调度、避免重复挂号”“检索准确率不低于 90% 靠什么保证”）
   - 用“怎么做/靠什么/如何保证”来问，不用“是否…/能否…”（是非题只能得到“是”，讲不出内容；“能否按期完成”应问成“六个月工期按什么节点推进、靠什么保证”）
   - level：主 / 次（主要问题 3—6 个，汇报中必须有页面讲清）
   - answer_sections：原文中能回答这个问题的章节键（写到小节）
   - answerable：能 / 部分
   - basis：一句话说明原文怎么回答
   - 问题问的是原文“做了什么、怎么做”；原文的空缺、待甲方明确的事项不是问题，放进 weak_points。同一件事不要既当问题又当薄弱点，问题之间也不要重复（如“精度怎么考核”与“泛化怎么验收”合成一题）

6. weak_points（薄弱点）：0—5 个，专家可能质疑、但原文没有讲清或没有给出依据的地方（如缺测试条件、缺责任主体、指标无测算依据）。
   这些不会上屏，交给汇报人准备答疑。写 q（专家可能怎么问）和 gap（原文缺什么）。
   文档自身的笔误、前后数字不一致不属于追问或薄弱点（已另行记录），不要写进来。

不要为了凑数编造原文没有依据的担忧；问题本身要能从原文内容推出来。
